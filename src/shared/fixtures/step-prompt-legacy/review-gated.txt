Choose exactly one next step: Build (changes requested), Finish (approved) — put its name, or the edge label shown in parentheses after it, in "next".

Use "status":"blocked" when this step's own work is NOT finished and you cannot finish it now (out of usage, a missing input, a decision only the user can make): say what remains in "reason". The run then stays on this step — it is resumed here later, or a person steps in — and nothing is handed to a next step. On a blocked handoff also add "waitingOn", saying what you wait on: "owner" (a decision, an answer, a credential, a permission — anything only a person can do), "resource" (a shared resource is busy: a lease, a slot), "dependency" (another issue or PR has to land first, or CI has to run), "environment" (a failure outside your work that should pass on a retry: network, a registry, a crashed tool), "usage_limit", or "other"; and "waitingRef" when it has a name (the lease's label, "#123"). For anything but "owner" this step is resumed by itself when that clears, a limited number of times. Put in "openQuestions" only questions the user must answer: a blocked handoff with open questions waits for the user and is not retried. The one exception: if another step is the right one to fix the problem you hit (for example a "changes requested" or "verification failed" option above), name it in "next" and the run goes there; this applies only to a corrective option, never approval or shipping, and only when you have no declared wait, owner question or permission hold. Otherwise set "next" to null.

Do not put anything after the closing </handoff> tag.
